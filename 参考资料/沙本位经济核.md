### 0.2 每日结算循环（规范序）

> 以下为 `GameData.AdvanceDay()` 的规范序，任何新增经济模块必须接入此流程：

```
第 N 天结算顺序：
1.  发车方案 → 今日趟数（保守3 / 标准4 / 加开5）
2.  计算日客流（常用公式：人口×信任系数×季节×(1-渗透)×服务系数）
3.  收入 = 客流 × 票价 × 趟数
4.  燃料费 = 油耗×日里程/100 × 车况系数 × 油价
5.  工资 = 月薪/30
6.  维护费 = 策略基准 × 车况系数 × 技能系数
7.  净收入 = 收入 − 燃料 − 维护 − 工资 → Money += 净收入
8.  信任变化 = 基础+1 + 员工分配 + 服务策略 + 对外策略
9.  车况变化 = 维护策略决定（含基础损耗）
10. 客流变化 = 员工分配 + 服务策略
11. 随机事件挂载（EventManager）
12. 沙能竞争挂载（SandRivalManager 日更新 + 30天行动轮）
13. 员工疲劳/经验日更新（CrewManager）
14. 订单日推进（OrderManager）
15. ClampStats（资金≥0，信任/车况钳制0-100）
16. 短期目标检查 → 自动切换
17. Day += 1 → 教程提示 → 刷新UI简报
```

### 0.5 经济参数来源（数据驱动）

- 代码中经济参数目前**硬编码在 `GameData.cs` 顶部常量区**（票价35/油耗58.5/油价15/月薪90000/天趟4等）。
- 设计目标：参数迁移至 `GameConfig`（已含 `moneyMultiplier/costMultiplier/passengerMultiplier` 等倍率）之外的**独立数值配置文件**（JSON/ScriptableObject），支持数值热改。
- 迁移优先级：票价→燃料→维护→工资（先做影响最大的四项）。

### 0.7 经济算法缺陷诊断与优化（v4.1 草案）

> 以下缺陷来自 `GameData.cs` 源码审视——不是"设计缺文档"，是**代码里真的写错了/写死了**。

#### 0.7.1 缺陷清单（按严重度）

| # | 缺陷 | 代码位置 | 后果 |
|---|------|----------|------|
| A1 | **季节系数是常量**：`SeasonModifier = 1.0f` 永远等于 1，春夏秋冬不存在 | GameData.cs 顶部 | 茶乡采茶季/货运旺季等于没做；设计文档写"1.0±0.2"但代码从未接上 |

#### 0.7.2 优化方案

**O1 季节系统接入（修 A1）**

```
SeasonModifier = 按 Day 计算（雾峰村茶乡四季）：
  春（3-5月）：采茶季 ×1.15   ← 客流主力
  夏（6-8月）：旅游 ×1.05
  秋（9-11月）：货运旺季 ×1.20 ← 货运收入加成
  冬（12-2月）：淡季 ×0.90

实现：Month = (Day % 360) / 30；按月份查表，替代常量。
```

**O2 沙能渗透接入（修 A2）**

```
客流公式中 (1 - SandPenetration) 的 SandPenetration
  从私有常量改为 → SandRivalManager.GetPenetration(当前城市)
  
（铁龙竞争系统的数值第一次真正流进经济核）
```

**O3 容量约束（修 A3）**

```
新增状态：CarCount（车厢数，初始2）、CapacityPerCar（30人）
日容量 = CarCount × CapacityPerCar × trips

实际客流 = min(需求客流, 日容量)
超额处理：
  - 需求 > 容量的 120%：产生"拥挤"负反馈，信任 -1/天（欠容量预警）
  - 需求 ≤ 容量：维持信任

车厢升级（经济扩张出口）：100,000沙币/节（基准价）
```

**O4 客流-信任非线性（修 A4）**

```
信任系数 TrustFactor 改为分段：
  Trust < 30  : 0.25 + Trust×0.005   （信任崩塌区，客流雪崩）
  30 ≤ T < 70 : 0.45 + T×0.008       （正常线性区）
  T ≥ 70      : 0.85 + (T-70)×0.003  （高信任饱和区，边际递减）

效果：掉信任惩罚更狠、攒信任前期明显、后期趋缓——符合现实口碑逻辑
```

**O5 工资动态化（修 A5）**

```
日工资 = Σ(员工职级月薪) / 30
  - 员工数与职级从 CrewManager 读取
  - 先民人事系统接入后：缺岗岗位 ×1.2 加班费
回退策略：若 CrewManager 未初始化，用固定 90,000/月兜底
```

**O6 月度财务闭环（修 A6）**

```
每 30 天（Day % 30 == 0）生成月报：
  月收入 / 月支出 / 月利润 / 现金流走势
  财政压力趋势线：月利润累计亏损 > X → 压力 +0.05
（为"财政压力趋势线"提供数据源）
```

**O7 破产保护入核（修 A7）**

```
经济核内置 CheckBankruptcy（Day 末调用）：
  资金 ≤ 0 且这月已经破产保护过 → 破产事件
  资金 ≤ 0 首次 → 触发「老陈紧急资金」叙事（10,000沙注入）
  资金 ≤ 0 二次 → 触发「政府救助」事件（5,000沙 + 政治压力 +0.1）
```

#### 0.7.3 优化后的结算循环（替换 0.2 第 2-7 步）

```
2.  计算日需求客流（含 O1 季节 / O2 渗透 / O4 信任分段）
2.5 计算日容量 = 车厢数 × 30 × 趟数
2.6 实际客流 = min(需求客流, 容量)；超额触发拥挤负反馈
3.  收入 = 实际客流 × 票价 × 趟数（货运收入预留 += 货运量×23×0.5）
4.  燃料费 = 油耗 × 里程/100 × 车况系数 × 油价 × 季节系数①
    ① 冬季油价 ×1.05（对应沙能弱点"夜间/冬季效率低"）
5.  工资 = Σ员工职级月薪 / 30（O5）
6.  维护费 = 策略基准 × 车况系数 × 技能系数（与 §十四 口径统一）
6.5 补贴 = 8000/30 × subsidyMultiplier（O8）
7.  净收入 = 收入 + 货运 + 补贴 − 燃料 − 维护 − 工资
```

> **实施建议**：A1/A2/A3 是三个"直改常量/直连系统"的快速修复（1-2 小时），A4-A8 各 0.5-1 天。全部完成后，经济核才真正"自己转起来"。已列入 `docs/for-ai/DEV_PLAN.md` P1 编码任务。

#### 0.7.4 补充缺陷：A9 客流口径单位不匹配（A3 实施时发现）

**现象**：
- 客流公式产出 ≈ **6-7 人（单趟）**：`8×(0.5+62×0.005)×1.15×0.85×1.06 ≈ 6.7`
- 代码初始 `ExpectedPassengers = 22` ≈ **日客流**（单趟×4趟：5.77×4≈23）——**口径不一致**
- A3 容量约束：`GetDailyCapacity = 2×30×4 = 240（日）` 却与单趟客流 min 比较 → **容量约束永远不会触发**（min(6.7, 240)=6.7）

**后果**：
1. UI 客流第 1 天显示 22，第 2 天结算后跳变为 ~7 —— 数值跳变，玩家困惑
2. 容量/拥挤系统形同虚设（需求 6.7 vs 容量 60/趟）
3. 设计文档称"单程上座率≈19%"，即 30 人车厢只坐 6 人 —— **游戏数值上不存在满座压力**

**方案 O9：统一口径 + 数值校准**

```
口径统一（推荐）：
- 万物按"单趟"计：客流系数产出单趟客流，容量 = 车厢数×30（单趟）
- 日客流 = 单趟客流 × trips（仅用于显示/短期目标）
- 收入 = 单趟客流 × 票价 × trips
- 拥挤判定：单趟客流 > 单趟容量×1.2

数值校准（否则容量系统永无意义）：
- 方案A：车厢容量 30→15 人，使 2 节=30 人/趟，上座率 6.7/30≈22%→仍偏低
- 方案B（推荐）：客流系数从 0.001 提到 0.0025，单趟客流 ≈ 17-19 人，
  上座率 ≈ 63%（2节包/30人容量），加开一班时逼近 75% → 容量与拥挤有真实压力
- 校准后初始日客流 ≈ 18人×4趟 = 72/天，与文档 §7.1"18人/天"叙事对得上
```

> **注意**：方案 B 属于**数值再平衡**，会推高收入预期，需同步调整 §7 盈亏表与成本（否则纯运营亏损消失，破坏"剧情是生命线"设计）。实施时以 A9 改造 + 数值参数化（0.5）一并处理，避免二次伤筋动骨。

#### 0.8 优化后数值演算验证（目标状态）

> 以 O1-O9 全部落地为前提，验证"容量约束可触发 + 亏损曲线合理"。

**设定**：Day 1=春季（×1.15），2 节车厢（60 人/趟），标准维护，信任 62，渗透 0.15，乘务员 2 级，客流系数 0.0025（O9-B）。

```
单趟客流 = 8000×0.0025 × 0.81 × 1.15 × 0.85 × 1.06 ≈ 16.8 人
日客流   = 16.8 × 4趟 = 67 人/天
上座率   = 16.8/30 = 56%（标准运行）

—— 加开一班（5趟，乘务员满）：17.5×5 ≈ 87 人/天，上座率 58% → 未拥挤
—— 信任 80 + 秋季（×1.20）：客流 = 20×0.9×1.2×0.85×1.06 ≈ 19.5 人/趟
    5趟 = 97 人/天 → 逼近容量 100（5趟×20人容量）→ 开始拥挤，触发负反馈
    ✓ 容量约束在这一刻"活了"：玩家需要加购车厢才能再压榨客流
```

#### 0.9 高阶经济算法（v4.1 扩展，供展示与深度设计）

> 本节提供经济核的进阶模型，用于：① 对外展示经济系统的专业性（立项/评审材料）；② 为后续玩法扩展（科技树/区域/赛季）提供算法基础。均未编码，按需实现。

##### 0.9.1 沙本位货币通胀模型（沙子锚定波动）

**背景**：沙币锚定标准工业沙（世界观扩展设定 §3.3.1）。若沙子供应受冲击（地缘/耗尽），沙币购买力波动——经济核可通过"沙子价格倍率"传导到全系统。

```
沙币购买力 P(月) = 基准购买力 × 沙供指数

沙供指数 = 1.0（基准）
  - 配额收紧事件：-0.10/次（铁龙/地缘博弈，可触发1-2次/年）
  - 新矿投产：+0.05/次（新闻事件）
  - 长期漂移：±1%/年（慢变量）

传导路径：
  沙供指数 ↓ → 沙子价格倍率 ↑（GameConfig）→ 燃料费/补给成本 ↑ → 全系统成本通胀
```

**游戏内表现**：通胀来临前新闻预告（"沙能配额或紧缩"），玩家可提前调策略（囤积/减少加开）。**展示价值**：经济核不是静态表，是**会呼吸的系统**。

##### 0.9.2 票价弹性系数（价格-客流权衡）

**背景**：票价目前固定 35 沙/人。开放票价调整后，需弹性系数防止"永远抬价"的最优解。

```
客流_新 = 客流_旧 × (当前票价/基准票价)^弹性系数

弹性系数（按线路定位）：
  - 民生线：-1.6（对价格极敏感，乘客穷）
  - 标准线：-1.2
  - 商业线：-0.7（商务客对价格不敏感）

示例（标准线，票价 35→40，+14%）：
  客流 = 客流 × (40/35)^-1.2 ≈ 客流 × 0.85 → 收入 = 0.85×1.14 ≈ 0.97×原收入
  → 提价 14% 只多赚 3%——高弹性使"杀鸡取卵"不划算，逼玩家靠服务/信任增收
```

**设计意图**：票价成为**策略旋钮而非数字游戏**——低价抢客流（民生定位）vs 高价保利润（商业定位），与线路定位系统（核心玩法循环 §3）呼应。

##### 0.9.3 现金流风险预警（破产概率模型）

**背景**：现有预警是固定阈值（§10）。引入**概率化破产模型**，让预警"会说话"：

```
破产概率（未来30天） = Φ((资金 + 预期30天净现金流) / 现金流波动)

简化实现（CLT近似）：
  日均现金流均值 μ = 最近7天净收入均值
  日均现金流波动 σ = 最近7天净收入标准差
  30天预期 = 资金 + 30×μ
  30天波动 = σ×√30
  破产概率 ≈ P(30天预期 < 0) ≈ 标准正态CDF(0 - 30天预期 / 30天波动)

示例：资金 12,000，μ=-1,400/天，σ=800
  30天预期 = 12,000 - 42,000 = -30,000
  Z = (0 - (-30,000)) / (800×√30≈4,383) ≈ 6.84 → 破产概率 ≈ 几乎必然
  → 预警从"资金<10,000"升级为"预计30天内破产（>95%）"——玩家看到的是结论而非阈值
```

**展示价值**：动态风险仪表盘（资金/预测/破产概率三个数字），比固定阈值专业得多，也是"数据驱动"理念的体现。

##### 0.9.4 季节回归模型（客流预测）

**背景**：玩家需要一个"敢信"的客流预测来规划车厢采购/加开决策（O3 容量决策的决策支撑）。

```
预测客流(第 D 天) = 季节基准(D) × 信任修正(D) × 渗透修正(D) × 服务修正(D)

- 季节基准：由 0.7 O1 的四季系数 + 前一年同段历史客流平滑（EWMA）
- 信任修正：A4 分段函数 + 信任动量（近7天变化方向，取±0.02）
- 渗透修正：1 - 当前渗透率
- 服务修正：1 + 乘务员等级×0.03

输出：客流预测 + 置信区间（±1σ，来自历史残差）
```

**设计意图**：把"看天行事"变成"有依据的运营"。展示价值在于——**经济核提供预测接口**，未来岁月叙事引擎/手机AI助手可以直接调用它，形成"AI 说：下月秋季客流将涨 20%，建议加购一节车厢"的闭环。

## 八、随机事件系统（保持游戏新鲜感）

### 8.0 设计原则（概率波动）

**避免硬编码**：所有数值添加概率波动
- **高波动参数**（±30%）：客运量、上座率、乘客满意度
- **中波动参数**（±15%）：油价、维护成本、事故概率
- **低波动参数**（±5%）：工资、基础补贴、燃料消耗

**波动公式**：
```
实际值 = 基础值 × (1 + 随机波动)
随机波动 = 随机数(-波动范围, +波动范围)
```

**示例**：
- 客运量基础值100人，波动范围±30%
- 实际值 = 100 × (1 + 随机数(-0.3, +0.3)) = 70-130人

## 十四、跨系统联动公式

### 事故概率计算

```
事故概率 = 基础概率(5%) × 车辆老化系数 × 司机专长系数 × 维护系数

其中：
- 车辆老化系数 = 1 + (100 - 车辆状态) / 50
- 司机专长系数 = 1 - (司机等级 × 0.15)
- 维护系数 = 1 - (最近7天维护次数 × 0.1)

示例：
- 车辆状态70，司机3级，最近维护2次
- 事故概率 = 5% × 1.6 × 0.55 × 0.8 = 3.52%
```

### 维护成本计算

```
实际维护费 = 基础维护费 × 车辆损耗系数 × 机械师专长系数

其中：
- 车辆损耗系数 = 1 + (100 - 车辆状态) / 100
- 机械师专长系数 = 1 - (机械师等级 × 0.1)

示例：
- 基础维护费15,000，车辆状态60，机械师5级
- 实际维护费 = 15,000 × 1.4 × 0.5 = 10,500沙币
```

### 乘客满意度计算

```
满意度 = 基础分(60) × 准点率系数 × 服务系数 × 车辆舒适度系数

其中：
- 准点率系数 = 0.8 + (准点率 × 0.4)
- 服务系数 = 1 + (乘务员等级 × 0.05)
- 车辆舒适度系数 = 0.7 + (车辆状态 / 200)

示例：
- 准点率90%，乘务员4级，车辆状态70
- 满意度 = 60 × 1.16 × 1.2 × 1.05 = 87.7分
```

### 燃料成本修正

```
实际燃料费 = 基础燃料费 × 车辆状态系数

其中：
- 车辆状态系数 = 1 + (100 - 车辆状态) / 200

示例：
- 基础燃料费24,225，车辆状态70
- 实际燃料费 = 24,225 × 1.15 = 27,859沙币
```
