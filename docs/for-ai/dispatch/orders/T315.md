### 2. P0 / P1 / P2 发现列表

#### 【P0 阻断性风险】

1. **P0-1 [源码可证]：`LaunchApp` / 任务切换未先对当前运行态任务执行快照归档，导致状态静默丢失**
   - **问题**：前台任务切换前缺少状态持久化触发点。
   - **证据**：`GameMainUI.cs` L2582-2635 `LaunchApp(string appName)` 中，当用户从桌面、Dock、通知或多任务切换启动 App 时，直接将 `activeTabletTask` 赋值并调用 `BuildXxxApp(win)`；未调用 `session.Capture(state)`，亦未将当前前台 App 的视图/数据状态存入 `TabletTaskSession` 的 LRU 缓存。
   - **触发条件**：前台打开 App A（例如设置页正在搜索或滚动，或记事本有未保存草稿），点击通知跳转或从快捷栏打开 App B。
   - **后果**：原 App A 的未持久化状态、滚动位置和子视图状态丢失，重新切回时只能完全重新初始化。
   - **建议修正**：在 `LaunchApp` 或任务切换逻辑入口处增加前置钩子：若当前 `activeTabletTask != null`，先执行 `ArchiveCurrentTaskSession()` 抓取当前快照并安全沉淀。

2. **P0-2 [源码可证]：实体 Escape 事件下潜与冒泡双重监听，存在击穿与二次误关 App 风险**
   - **证据**：`GameMainUI.cs` L434-441 在 `root` 注册了 `KeyDownEvent(TrickleDown.TrickleDown)`；紧接着在 L442-463 又在 `root` 注册了普通冒泡阶段的 `KeyDownEvent`。App 内部弹窗/二级视图如果注册自身 KeyDown，执行时机介于两者之间。L449 的 `!dispatchingSystemBack` 标志重入防护未做原子保护，且两处监听器对 `TabletRebindAction` 判定条件分散。
   - **触发条件**：用户在 App 嵌套弹窗中按下 Escape；或者在系统面板处于打开过渡态时连击 Escape。
   - **后果**：弹窗可能消费了按键但未完全阻止事件流，导致外层 L459 的 `ReturnToTabletHome()` 紧接着被触发，直接连同 App 一并关闭退回桌面。
   - **建议修正**：收口到统一的键盘调度中心 `HandleSystemEscape()`，严格按照优先级分层判断并一次性消费：`TabletRebindAction` > `CloseSystemPanel` > `AppModal/Subpage` > `ReturnToTabletHome` > `CloseRecentTasks`，必须严格单一出口拦截并 `StopImmediatePropagation()`。

3. **P0-3 [源码可证]：`TabletSettingsAppUI` 响应式单列/双列重排时未保存滚动位置与搜索输入草稿**
   - **证据**：`TabletSettingsAppUI.cs` 中当窗口尺寸改变跨越单双列阈值，或点击不同大类时，直接清空父容器并执行 `BuildSettingsPage(win)`。搜索输入框（`TextField`）的 `value` 与 `ScrollView` 的 `scrollOffset` 在销毁旧 DOM 前未提取缓存。
   - **触发条件**：平板窗口宽度在双列侧栏与单列窄屏之间自适应临界切换，或用户在设置页子分类与主分类间频繁切换。
   - **后果**：用户输入的搜索关键词被重置，滚动列表跳回顶部。
   - **建议修正**：在 `TabletSettingsAppUI` 抽离 `SettingsViewState`，包含 `lastSearchQuery`、`lastScrollOffset`、`activeCategory`，在重新渲染前缓存，渲染完成后通过 `schedule.Execute` 恢复。

4. **P0-4 [源码可证]：顶层边缘手势采用 TrickleDown 阶段抢夺 Pointer 事件，与 App 内部滚动条/滑块严重冲突**
   - **证据**：`GameMainUI.cs` L464-467 在 `root` 顶层注册了 `PointerDownEvent`、`PointerMoveEvent`、`PointerUpEvent`，全部携带 `TrickleDown.TrickleDown`。
   - **触发条件**：用户在贴近屏幕边缘的 `ScrollView`、`Slider` 或横向滑动卡片上执行拖拽操作。
   - **后果**：下潜阶段手势检测直接截获指针并启动系统边缘判定，底层的 UI Toolkit 原生 `ScrollView` 无法收到 PointerMove，造成界面无法滚动或滑块卡顿失灵。
   - **建议修正**：对手势识别加入命中测试过滤器：若 `evt.target` 属于 `ScrollView`、`Slider`、`TextField` 内部元素，且位移未超出系统级防误触阈值（Slop 判定），禁止下潜拦截；或将边缘触控感应区域严格限制在专用的半透明把手/边缘感应条内。

#### 【P1 逻辑与交互缺陷】

1. **P1-1 [源码可证]：系统面板遮罩（Scrim）未绑定完整的事件吞噬，导致穿透点击底层 App**
   - **证据**：`TabletShellView.cs` 中通知/控制面板展开时，背景 scrim 遮罩层未在所有渲染分支下显式声明 `pickingMode = PickingMode.Position` 并绑定阻断事件，且在 `ClosePanel` 触发时缺少焦点恢复机制。
   - **后果**：用户误触背景遮罩时可能穿透触发底层 App 界面按钮。
   - **建议修正**：给遮罩层统一部署 `ClickEvent` / `PointerDownEvent` 监听器，调用 `ClosePanel()` 并执行 `evt.StopPropagation()`。

2. **P1-2 [源码可证]：`TabletTaskSession` 内存回收使用 `GC.GetTotalMemory` 无法反映移动端真实内存压力**
   - **证据**：`TabletTaskSession.cs` 依靠托管堆内存轮询计数作为后台 App 视图回收（Trim/Evict）的触发依据。
   - **触发条件**：在 Windows 桌面运行时托管堆波动，或在 Android 移动端运行。
   - **后果**：在 Android 平台该指标与 Linux/Android 系统的物理 OOM 压力完全脱节，无法响应真实系统低内存警告；而在托管堆产生临时垃圾峰值时，却错误地杀死了用户的后台 App 视图。
   - **建议修正**：接入 Unity 的 `Application.lowMemory` 原生系统回调；仅在收到系统低内存警告时才销毁后台 DOM，平时只做轻量的状态冻结。

3. **P1-3 [高风险推断]：面板动态高斯模糊缺乏离屏缓存，可能引发频繁 GC 顿挫**
   - **证据**：`GameMainUI.cs` L106 `tabletShellView?.ClearBlurredBackground()` 与面板开关联动，在缺乏 ComputeShader 降采样缓存的情况下频繁生成/销毁临时全屏 Texture。
   - **建议修正**：使用固定分辨率的双缓冲 RenderTexture 循环复用，避免每次展开面板都重新申请分配内存。

4. **P1-4 [源码可证]：按键重绑定时按 Escape 会产生与应用退出的竞争状态**
   - **证据**：`TabletSettingsAppUI` 在监听重绑定输入时，如果取消重绑定的 Escape 键处理后未加冷却保护或 Token 标记，可能在同一帧被外层检测捕获。
   - **建议修正**：在重绑定状态注销后设置 1 帧的按键消耗标记（`consumedKeyToken`），防止同键外泄。

### 5. 总结与建议

- **评估结论**：**建议先修复指定阻断项（P0 列表），再继续铺开后续业务 App 交互**。
- **整改优先级**：
  1. `GameMainUI.cs` 的 Escape 返回逻辑收口为单一分发器，消除冒泡击穿（解决 P0-2）；

  3. 在 `TabletTaskSession` 与 `LaunchApp` 建立规范的任务切出与快照保存流程（解决 P0-1）。
