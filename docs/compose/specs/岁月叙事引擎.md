## 一、设计哲学

### 1.1 叙事引擎的定位

> 叙事不是"剧情插播"，而是"世界在说话"。

**岁月叙事引擎**的名字来源于游戏中的 AI 角色"岁月"——一个 2053 年制造、沉睡 23 年的强 AI 原型。引擎以她命名，因为她的核心功能就是：**读取世界状态，说出这个世界的真实故事**。

### 1.2 三层叙事架构

```
第一层：硬编码主线（Scripted）
  - 序章剧本（prologue_01 ~ prologue_10）
  - 关键剧情节点（不可跳过）
  - 由 JSON 剧本驱动，100% 可控

第二层：模板化叙事（Template-based）
  - 根据世界状态匹配事件模板
  - 参数化填充（城市名、角色名、数值）
  - 当前实现阶段

第三层：AI 生成叙事（AI-generated）
  - 读取种子结构 + 趋势线 + 角色关系
  - 生成结构和时机都匹配当前世界的事件
  - 未来实现阶段
```

### 1.3 叙事引擎的输入输出

```
输入：
  - 世界种子（城市依赖图、资源分布、政治倾向）
  - 五条趋势线的当前位置
  - 玩家与角色的关系、角色与角色的关系
  - 最近的玩家操作历史
  - 当前游戏时间（第几天）

输出：
  - 新闻事件（全屏滚动新闻格式）
  - NPC 对话（VN 对话框格式）
  - 任务描述（订单/任务格式）
  - 叙事文本（旁白/描述格式）
```

### 2.3 故事可能性评估器

```csharp
// 评估哪些故事在当前世界状态下是"可能的"
public class StoryEvaluator
{
    public StoryPossibility[] Evaluate(NarrativeContext context)
    {
        var possibilities = new List<StoryPossibility>();
        
        // 1. 检查种子决定的"可能性空间"
        //    - 城市依赖图决定了哪些事件链是可能的
        //    - 政治倾向决定了哪些解决方案是可能的
        
        // 2. 检查趋势线位置
        //    - 信任低 → 乘客抱怨事件可能
        //    - 沙能渗透高 → 沙能收购事件可能
        //    - 设施老化高 → 设备故障事件可能
        
        // 3. 检查角色关系
        //    - 忠诚度低 → 员工离职事件可能
        //    - 疲劳高 → 员工请假事件可能
        
        // 4. 检查冷却（避免重复）
        //    - 同类事件在冷却期内不触发
        
        return possibilities.ToArray();
    }
}
```

### 3.2 模板匹配算法

```
输入：NarrativeContext（当前世界状态）
输出：匹配的模板列表（按优先级排序）

算法：
1. 遍历所有模板
2. 对每个模板，检查 conditions 是否满足
   - 数值条件：trust.min ≤ current ≤ trust.max
   - 状态条件：role == "driver" 等
   - 城市条件：仅当该城市有相关事件
3. 计算匹配分数（优先级 × 条件满足度）
4. 按分数排序，取前 N 个
5. 检查冷却期（cooldown_days）
6. 返回可触发的模板
```

### 3.3 参数化填充

```csharp
public class TemplateFiller
{
    public string Fill(string template, NarrativeContext context)
    {
        // 替换参数占位符
        // {city} → 当前城市名
        // {incident_type} → 从参数数组中随机选一个
        // {delay_hours} → 根据车况计算（车况越低，延迟越长）
        // {player_name} → 玩家别名或"林彪悍"
        
        string result = template;
        result = result.Replace("{city}", context.currentCity);
        result = result.Replace("{incident_type}", PickRandom(parameters.incident_type));
        result = result.Replace("{delay_hours}", CalculateDelay(context.trainCondition));
        return result;
    }
}
```

| 好感度 | 语气 | 回复倾向 | 对话长度 |
|--------|------|----------|----------|
| 90-100 | 热情友好 | 积极、帮助、主动提供信息 | 80-100字 |
| 70-89 | 正常 | 中立、合作、回答问题 | 50-80字 |
| 50-69 | 冷淡 | 保留、敷衍、简短回答 | 30-50字 |
| 30-49 | 不满 | 抱怨、拒绝合作、态度差 | 10-30字 |
| 0-29 | 敌对 | 对抗、威胁、离开 | 不回复 |

### 5.2 岁月与平板内 RDA 的关系（同机双 AI）

```
主角随身终端：岁月的小米平板（Xiaomi Pad 36 Ultra，澎湃32系统·朝鲜特供版）
主角没有自己的手机——唯一随身终端就是这台平板（中国电子工业绝唱）

两条 AI 线（同一台平板内并存）：
  - 岁月（0721）：13岁二次元少女形态的强 AI，感性、不完美、被封印
    - 投影形态随时陪伴主角（车内/站台/办公室皆可投影出现）
    - 依靠平板算力投影；知道很多秘密（爷爷的事情、沙能的真相）
    - 但被某种协议限制，不能直接说出
    - 随着好感度提升，逐渐解锁记忆
    - 少女形态：会好奇、会碎碎念、会替主角操心（买炸鸡、建议休息）

  - RDA（Railway Decision Assistant）：理性、精确、工具 AI
    - 平板内的独立 App/服务，运行玩家自己的 API Key
    - 叙事包装为"远程调用学校服务器"
    - 提供运营建议，但不参与剧情；界面为平板里的常规 App 对话框
    - 与岁月"同机不同层"：岁月是系统级投影，RDA 是应用级助手

  剧情张力：
    - 岁月：感性，会说"我选择相信你"（投影在身边，能触手可及）
    - RDA：理性，会说"根据数据，建议你..."（平板的 App 弹窗）
    - 同机共存强化身份：岁月是"陪伴者"，RDA 是"工具"
    - 后期：两条 AI 线可以产生交互（岁月调侃 RDA 是"只会算数的隔壁班同学"）
```

### 5.3 岁月记忆解锁机制

```
好感度 0-30：岁月只回答运营相关问题
好感度 31-60：岁月开始透露过去
好感度 61-80：岁月讲述爷爷的故事
好感度 81-100：岁月揭露沙能的真相

好感度提升方式：
  - 剧情对话中选择理解/支持岁月的选项
  - 定期和岁月聊天（每天一次）
  - 完成岁月提出的任务

好感度降低方式：
  - 忽视岁月的建议
  - 在对话中选择冷漠/对抗选项
  - 长期不互动
```

## 六、叙事节奏控制

### 6.1 事件密度

```
游戏阶段    事件密度    说明
序章（Day 0-4）  高    脚本驱动，每场景都有事件
生存期（1-3月）  中    每3-5天一个事件，模板为主
发展期（3-6月）  中低  每5-7天一个事件，质量高于数量
扩张期（6月+）  低    每7-10天一个事件，重大事件为主
```

### 6.2 事件类型分布

| 类型 | 占比 | 示例 | 触发方式 |
|------|------|------|----------|
| 运营事件 | 40% | 设备故障、客流变化 | 趋势线检测 |
| 角色事件 | 25% | 员工对话、岁月回忆 | 好感度/疲劳检测 |
| 竞争事件 | 20% | 沙能行动、价格战 | 沙能AI轮 |
| 政治事件 | 15% | 政策变化、补贴调整 | 政治周期 |
